# 장기 분석판

Yixin-Board 를 장기로 옮긴 도구. 판을 마음대로 고쳐놓고, 그 국면을 세계 최강
장기 엔진에게 그대로 물려서 실시간으로 분석한다. 급수를 골라 한 판 두고,
둔 기보를 한 수씩 되짚어 볼 수도 있다.

엔진은 **Fairy-Stockfish** 를 브라우저(WebAssembly)에서 돌리고, 장기 전용
NNUE 신경망(`janggi-9991472750de.nnue`, 기존 평가함수 대비 +1128 Elo)을 얹었다.
프로 기사보다 강하다.

화면은 하는 일에 따라 셋으로 나뉜다.

| 모드 | 하는 일 |
|---|---|
| **대국** | 급수를 골라 엔진과 둔다 |
| **분석** | 판을 고쳐놓고 그 국면을 분석한다 |
| **복기** | 둔 기보를 한 수씩 되짚는다 |

배치는 한국 장기 앱들을 따랐다. 판이 화면 높이를 꽉 채우고, 위아래로
대국자 카드가 붙는다. 자세한 것은 [화면 배치](#화면-배치) 참고.

## 시작하기

```bash
npm install
npm run dev      # http://localhost:5173
```

`npm run dev` 는 실행 전에 `scripts/fetch-engine.mjs` 를 돌려서 엔진 파일을
`public/engine/` 에 채운다. 처음 한 번만 약 13MB(엔진 1.6MB + 신경망 11.3MB)를
받고, 그 뒤로는 있는 파일을 쓴다. 이 파일들은 용량 때문에 저장소에 넣지 않는다.

> **신경망 받기가 실패하면** — 신경망은 남의 구글 드라이브 링크에서 받는다.
> 링크가 깨졌다면 <https://fairy-stockfish.github.io/nnue/> 에서
> `janggi-9991472750de.nnue` 를 직접 받아 `public/engine/` 에 넣으면 된다.
> 파일 이름은 그대로 두어야 한다.

```bash
npm test          # 순수 로직 테스트 (브라우저·엔진 없이)
npm run build     # 프로덕션 빌드
npm run preview   # 빌드 결과를 헤더까지 갖춰서 확인
npm run verify-engine   # 엔진만 따로 점검 (브라우저 없이)
```

## 반드시 알아야 할 제약: COOP/COEP

엔진은 멀티스레드 탐색에 `SharedArrayBuffer` 를 쓰고, 브라우저는 아래 두 헤더가
있어야만 그걸 허용한다.

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

`vite.config.ts`(개발·미리보기)와 `vercel.json`(배포)에 이미 넣어뒀다. 파일을
그냥 열거나(`file://`) 헤더 없는 정적 서버에 올리면 **엔진이 시작되지 않는다.**
같은 이유로 외부 웹폰트를 쓰지 않고 시스템 폰트만 쓴다.

올릴 곳을 고를 때 이 제약이 갈린다.

| 호스팅 | 가능 여부 | 비고 |
|---|---|---|
| Vercel | ✅ | `vercel.json` 이 이미 준비돼 있다 |
| Netlify / Cloudflare Pages | ✅ | 헤더 설정을 직접 옮겨야 한다 |
| **GitHub Pages** | ❌ | **응답 헤더를 지정할 수 없다** |

GitHub Pages 는 커스텀 헤더를 붙일 방법이 없어서 이 앱이 돌아가지 않는다.
굳이 쓰려면 `coi-serviceworker` 같이 서비스 워커로 헤더를 흉내 내는 우회가 필요하다.

## 기능

### 대국

**급수를 골라 둔다.** 18급부터 9단까지 27단계를 드롭다운에서 고른다. 급수마다
한 수에 걸리는 어림 시간이 이름 옆에 함께 적힌다(`9단 — 약 20초`). 얼마나 기다려야
하는지 모르는 것이 다른 장기 앱에서 가장 많이 나오는 불만이라 미리 보여준다.
급수를 어떻게 만들었는지는 아래 [급수는 무엇으로 만들었나](#급수는-무엇으로-만들었나) 참고.

초·한 중 아무 쪽이나 잡을 수 있고, 엔진끼리 두는 것을 구경할 수도 있다.
상차림은 대국을 시작하기 전에 양쪽 따로 고른다. **랜덤**을 고르면 넷 중 하나를
무작위로 잡아 초반이 매번 달라진다. 무르기·한수쉼·기권을 지원한다.

**규칙** — 표준(빅장 있음·점수제), 현대(카카오 호환, 빅장 없음·수 반복 금지),
전통(빅장 무승부·점수제 없음) 중에 고른다. 승부가 어떻게 갈리는지를 정하는 것이라
대국 설정이고, 상차림과 같이 **판이 시작되면 잠긴다** — 두던 중에 승부 조건이
바뀌면 안 된다.

**200수 제한** — 표준·현대에서는 양쪽 합해 200수를 넘기면 기물 점수로 승부를 가린다.
카카오장기가 쓰는 값이라 그대로 맞췄다. 여기가 어긋나면 그쪽에서 온 사람은 끝나야 할
판이 안 끝난다고 느낀다. 전통 규칙에는 점수제가 없으므로 걸리지 않는다.

**한(漢)의 덤이 점수 옆에 보인다.** 한은 후수라 1.5점을 미리 받는데, 그게 안 보이면
"왜 내가 앞서 있지" 하게 된다. 대국자 카드에 `덤 1.5` 로 붙여 둔다.

**시계** — 제한시간과 초읽기를 쓴다. 기본은 10분 + 30초 초읽기 3회이고,
대국 패널에서 바꾸거나 끌 수 있다. 프리셋에 없는 조합은 **직접 입력**으로
맞춘다(제한시간 분 · 초읽기 초 · 회수).

- 시계는 **첫 수가 놓여야 돈다.** 급수를 고르고 상차림을 맞추는 동안 시간이
  깎이면 곤란하기 때문이다.
- 제한시간이 바닥나면 초읽기로 넘어간다. 한 회 안에 두면 회수가 줄지 않고
  그 회가 처음부터 다시 찬다. 회를 넘기면 회수가 하나 줄고, 다 쓰면 시간패다.
- 기보를 되짚는 중(기보 끝이 아닐 때)이나 다른 모드에서는 멈춰 있다.
- **마지막 5초가 되면 숫자가 커지고 붉어진다.** "남은 시간을 잘 알려주지 않아
  시간패했다" 는 불만이 장기 앱마다 나온다. 숫자를 하나 더 띄우면 초읽기 표시와
  겹쳐 두 번 나오므로, 있던 숫자를 바꾸기만 한다.

**소리** — 세 가지가 다르다.

| 동작 | 소리 |
|---|---|
| 기물을 집을 때 | 얕고 짧은 "톡" — 알을 판에서 살짝 드는 소리 |
| 기물을 놓을 때 | 단단한 "딱" |
| 기물을 잡을 때 | 두 번 닿는다 — 상대 알을 걷어내고 그 자리에 놓는다 |

음원 파일이 아니라 Web Audio 로 그 자리에서 만든다. 이유는 셋이다. 이 도구는
인터넷 없이도 돌아가야 하고, 녹음 파일은 출처와 라이선스를 달고 다니며,
합성이면 둘 때마다 높이를 조금씩 흔들어 기계 같은 반복을 피할 수 있다.

**훈수**를 켜면 두는 동안 엔진의 추천수가 보인다. 기본은 꺼져 있다. 이때 훈수는
상대 급수와 무관하게 언제나 전력으로 본다. 약한 엔진이 내놓는 훈수는 도움이
되지 않기 때문이다. 같은 이유로 훈수가 꺼져 있으면 형세 그래프도 띄우지 않는다.
그래프 자체가 엔진의 평가를 그대로 흘리는 것이라서다.

### 분석

**판 편집** — 팔레트에서 기물을 고르고 교차점을 누르면 놓인다. 기물을 끌어서
옮기고, 판 밖으로 끌어내면 지워진다. 궁이 없거나 사·궁이 궁성 밖에 있으면 경고가
뜬다. FEN 을 붙여넣거나 복사할 수 있다.

**고치는 동안에도 분석이 돈다.** 이게 이 도구를 만든 이유다. 기물을 하나 옮길
때마다 엔진이 그 국면을 다시 판다. 편집을 마칠 때 판이 그대로면 두던 기보를
건드리지 않고, 달라졌을 때만 새 시작 국면으로 삼는다.

**실시간 분석** — 국면이 바뀌면 그 자리에서 다시 판다. 후보수는 최대 8개까지,
평가치는 항상 초(楚) 기준이다. 줄에 마우스를 올리면 판에 화살표가 뜨고, 누르면
그 수를 둔다.

**이길 확률** — 평가치 옆에 `62%` 가 함께 붙는다. `+1.20` 은 장기를 오래 둔 사람에게만
감이 오지만 확률은 처음 보는 사람도 안다. 후보수마다 붙으므로 "1순위 60%, 2순위 58%면
별 차이 없구나" 가 보인다. **다만 어림값이다** — 근거는 아래
[이길 확률은 어떻게 뽑나](#이길-확률은-어떻게-뽑나) 참고.

규칙은 **대국 패널**에 있다(아래 참고). 엔진 패널에는 후보수·스레드·해시·생각시간만
남겼다 — '얼마나 깊게 볼까' 와 '이 판을 어떻게 둘까' 는 성격이 다르다.

### 복기

기보를 처음부터 끝까지 한 수씩 엔진에게 물어보고, 실제로 둔 수와 견준다.
성적표에 **일치율**(엔진이 고른 수와 같은 수를 둔 비율)과 한 수당 평균 손해가 함께 나온다.
수마다 **최선수 / 좋은 수 / 부정확 / 실수 / 악수** 등급이 붙고, 고른 수에는
"어디다 두는 게 좋았는지" 와 그 이유가 붙는다. 최선수는 판에 화살표로 뜬다.

깊이는 빠름(10만) · 보통(50만) · 정밀(200만 노드) 중에 고른다. 중간에 그만둬도
거기까지는 남는다. 복기가 끝나면 그 점수로 형세 그래프를 다시 그린다. 실시간
분석 때 찍힌 값보다 깊이가 고르기 때문에 훨씬 정확하다.

설명을 무엇으로 만드는지는 아래 [복기는 무엇을 근거로 설명하나](#복기는-무엇을-근거로-설명하나) 참고.

### 설정은 브라우저에 남는다

급수·시계·규칙·내가 잡을 쪽·훈수·엔진 설정·복기 깊이·판 뒤집기를 localStorage 에
남긴다. 새로고침할 때마다 같은 것을 다시 고르지 않아도 된다.

**남기는 것은 설정뿐이고 판은 남기지 않는다.** 판까지 되살리면 어제 만지다 만
이상한 국면이 이유도 없이 떠 있게 된다. 새로 열면 새 판이고, 다만 손잡이는
어제 맞춰둔 자리에 있다. 같은 이유로 상차림도 남기지 않는다 — 그건 설정이 아니라
판 자체라서 되살리려면 기보를 건드려야 한다.

**읽어온 값은 믿지 않는다.** localStorage 는 사람이 직접 고칠 수 있고, 예전 판에서
저장해 둔 값이 지금은 없는 급수일 수도 있다. 그래서 값마다 "지금도 쓸 수 있는
모양인지" 를 확인하고 아니면 기본값으로 되돌린다. 이상한 값이 들어가도 다음
실행에서 저절로 낫는다 — 이게 없으면 사용자가 빠져나올 방법이 없다.

저장이 막힌 브라우저(사생활 보호 모드, 저장 차단)에서도 앱은 그냥 돈다. 읽기·쓰기
실패는 조용히 넘기고 기본값으로 간다.

### 어느 모드에서나

**대국 상태** — 장군을 맞으면 궁이 붉게 뛰고 배너가 뜬다. 외통이면 누가 이겼는지
알려주고 더 둘 수 없게 막는다. 장기에는 한수쉼이 있어서 외통이어도 합법수가 0이
되지 않으므로, "장군인데 한수쉼 말고는 둘 게 없음" 을 기준으로 판정한다.

**상차림** — 원앙마(안상), 양귀마(바깥상), 왼귀마(왼상), 오른귀마(오른상).
양쪽이 따로 고른다. 지금 판이 어떤 차림인지도 되읽어서 표시한다.
`면상`은 별도의 차림이 아니라 귀마 차림에서 상을 면자리로 올리는 포진이라
프리셋에 없다.

**기보 저장·불러오기** — 시작 국면과 수순, 평가치, 그리고 누가 어느 쪽을 어떤
급수로 잡았는지와 승부 결과까지 JSON 으로 담는다(`janggi-board/2`).
급수와 결과가 없던 첫 형식(`janggi-board/1`)도 그대로 읽는다.

**키보드** — `←` `→` 앞뒤로, `Home` `End` 처음·끝, `F` 판 뒤집기,
`space` 분석(대국 모드에서는 훈수) 켜고 끄기.

## 화면 배치

페이지는 스크롤되지 않는다. 화면 높이를 그대로 받아 쓰고, 넘치는 것은 오른쪽
패널 칸이 자기 안에서 스크롤한다. **판의 크기는 폭이 아니라 남은 높이가 정한다.**
세로가 짧은 창에서도 판 전체가 잘리지 않고 들어가야 하기 때문이다.

대국 모드에서는 판 위아래에 대국자 카드가 붙는다. 누가 어느 쪽을 잡았는지,
기물 점수, 잡아낸 기물, 남은 시간이 한 줄에 들어가고, **둘 차례인 쪽만**
흰 바탕으로 띄운다.

카드를 판과 같은 너비로 맞추는 게 생각보다 까다로웠다. 판의 너비는 남은
높이에서 나오는데, 카드 너비를 CSS 로 판에 맞추려 하면(`width: fit-content`)
이번에는 카드가 판의 너비를 정해버려서 서로 물고 돈다. 실제로 그렇게 짰더니
판이 남은 높이를 절반도 안 썼다. 그래서 판은 칸 전체 너비 안에서 자유롭게
크게 두고, 다 그려진 뒤의 너비를 재서(`ResizeObserver`) 카드에 넘긴다.

화면이 작을 때는 이렇게 물러선다.

| 조건 | 하는 일 |
|---|---|
| 세로 780px 이하 | 페이지 여백과 카드 사이 틈을 더 좁힌다 |
| 판 자리가 280px 미만 | 판을 더 줄이지 않고 판 칸 안에서 스크롤한다 |
| 가로 900px 이하 | 풀스크린을 포기하고 위아래로 쌓아 스크롤한다 |

판에 높이를 한 줄이라도 더 주려고 두 가지를 했다.

- **모드 탭을 제목 줄 안에 넣었다.** 설명이 붙은 카드 세 장이 한 줄을 통째로
  차지해 세로 57px 을 먹고 있었다. 설명은 툴팁으로 옮겼다.
- **판 안쪽 여백을 56 → 46 으로 줄였다.** 격자가 판 넓이에서 차지하는 몫이
  83% 에서 86% 로 늘었다. 좌표 숫자와 가장자리 기물이 겨우 스치지 않는 선이다.

1440×900 기준으로 판이 575×633 에서 **645×713** 이 됐다.

**글자는 어디서나 16px 아래로 내려가지 않는다.** 예전에는 11~14px 짜리 잔글씨가
곳곳에 있었다. 화면은 촘촘해 보이지만 판 앞에 앉아 한 판 두는 동안 읽기에는
작다. 화면이 작다고 글자까지 줄이지는 않는다 — 좁아지면 여백을 줄인다.

색은 **화이트 한 가지**다. 장기판 자체가 밝은 나무색이라, 판 둘레가 어두우면
판만 떠 보이고 눈이 아프다.

## 급수는 무엇으로 만들었나

한 급수는 **(Skill Level, 노드 수)** 한 쌍이고, 18급부터 9단까지 27칸이다.
표는 `src/engine/levels.ts` 에 있다. 어떻게 여기까지 왔는지는 전부 엔진에 직접
물어보고 1,120판을 붙여본 결과다.

### UCI_Elo 는 쓰지 않는다

엔진에 `UCI_LimitStrength` / `UCI_Elo`(500~2850) 옵션이 있어서 이것부터 시험했다.
장기 변형에서 Elo 를 바꿔가며 같은 국면을 돌린 결과는 이랬다.

```
Elo  500 | i4h4 b1c3 i4h4 b1c3 | depth≈15
Elo 1000 | a4b4 a4b4 i4h4 i4h4 | depth≈15
Elo 1800 | h1g3 b1c3 b1c3 b1c3 | depth≈15
Elo 2850 | a4b4 b1c3 b1c3 b1c3 | depth≈16
```

500 이나 2850 이나 똑같이 멀쩡한 수를 낸다. 이 환산표는 체스용으로 맞춰진 것이라
장기에는 눈금이 붙지 않는다. 숫자만 그럴듯하고 실제로 약해지지 않아서 버렸다.

### Skill Level 은 먹힌다

```
초기 국면에서 여섯 번씩 (300ms)
  Skill  20 | 서로 다른 수 1/6   ← 여섯 번 다 같은 최선수
  Skill   0 | 서로 다른 수 3/6
  Skill -20 | 서로 다른 수 2/6   ← 최선수를 아예 안 고름
```

종반 국면에서는 더 선명하다. 차를 쓸 수 있는 자리에서 Skill -20~-5 는 여덟 번 중
여덟 번 궁만 제자리에서 꼬물거렸고(`e1d1` `e1f1` `e1e1`), Skill 10~20 은 여덟 번 중
일고여덟 번 차를 움직였다.

### 시간이 아니라 노드로 자른다

`go nodes N` 은 정확히 N 노드에서 끊긴다 — 요청 1,000 → 실제 1,000, 요청 100만 →
실제 1,000,679. 시간으로 자르면 빠른 PC 의 3급이 느린 PC 에서는 5급이 된다.
노드로 자르면 어느 기기에서나 같은 급수다.

다만 약한 급수는 2천 노드를 눈 깜짝할 새에 보고 끝내므로, 최소 생각 시간
(`MIN_THINK_MS`)을 따로 둔다. 안 그러면 대국 같지가 않다.

### 27칸의 간격은 자가대국으로 쟀다

급수를 27칸으로 자르면 이웃한 두 칸의 차이는 아주 작다. 그 차이를 자가대국으로
직접 확인하려면 한 쌍에 수백 판이 필요하고, 쌍이 26개면 며칠을 부어도 모자란다.
그래서 순서를 뒤집었다.

1. 두 손잡이를 **하나의 강도 곡선**으로 묶는다. `t` 는 0(가장 약함)에서
   1(가장 셈)로 가는 눈금이다.

   ```
   Skill Level = -20 + 40t
   노드        = 1,500 · (5,000,000 / 1,500)^t
   ```

2. 그 곡선 위에 서로 확실히 구분되는 **기준점 13개**를 찍고, 이웃 쌍과 한 칸
   건너뛴 쌍끼리 실제로 붙인다.
3. 승패를 **Bradley-Terry** 로 풀어 기준점마다 레이팅을 낸다.
4. 그 레이팅 눈금 위에 급수 27칸을 앉힌다.

스크립트는 `scripts/ladder-selfplay.mjs` 다. 6코어 PC 에서 네 판씩 동시에 돌려
**85분 동안 1,120판**을 뒀다. 상차림 16가지를 돌려가며 색을 번갈아 잡았다.

**이웃한 기준점끼리**

| 대결 | 위쪽 승률 | 판수 |
|---|---|---|
| C1 vs C0 | 53% | 100 |
| C2 vs C1 | 52% | 100 |
| C3 vs C2 | 54% | 100 |
| C4 vs C3 | 63% | 100 |
| C5 vs C4 | 59% | 85 |
| C6 vs C5 | 86% | 47 |
| C7 vs C6 | 69% | 26 |
| C8 vs C7 | 100% | 14 |
| C9 vs C8 | 81% | 8 |
| C10 vs C9 | 100% | 5 |
| C11 vs C10 | 75% | 4 |
| C12 vs C11 | 88% | 4 |

**한 칸 건너뛴 기준점끼리** — 65% · 61% · 66% · 73% · 94% · 87% · 100% · 100% ·
100% · 88% · 88%

**23쌍 전부 위쪽이 앞섰다. 역전이 하나도 없다.**

- 이웃 쌍을 전부 합치면 593판에서 위쪽 승률 **61.0%**
- 한 칸 건너뛴 쌍은 527판에서 **72.6%**

솔직하게 적어두면, 아래쪽 쌍을 하나씩 떼어놓고 보면 100판에 53%·52%·54% 라
그 한 쌍만으로는 통계적으로 유의하지 않다(표준오차가 5% 다). 하지만 23쌍이 모두
같은 방향으로 나올 확률은 동전 던지기로 1,200만 분의 1이고, 한 칸 건너뛴 쌍은
65~66% 로 분명히 갈린다. **한 칸 차이는 작고 두 칸 차이는 확실하다** — 눈금이
이 정도면 촘촘한 것이다. 한 칸 차이가 압승이면 27칸으로 나눌 이유가 없다.

**기준점 레이팅** (가장 약한 쪽을 0점으로)

| 기준점 | Skill | 노드 | 레이팅 | 판수 |
|---|---|---|---|---|
| C0 | -20 | 1,500 | 0 | 200 |
| C1 | -17 | 2,700 | 40 | 300 |
| C2 | -14 | 4,900 | 78 | 400 |
| C3 | -11 | 8,700 | 108 | 400 |
| C4 | -8 | 15,700 | 195 | 340 |
| C5 | -6 | 28,000 | 276 | 263 |
| C6 | -3 | 51,000 | 581 | 145 |
| C7 | 0 | 91,000 | 673 | 81 |
| C8 | 3 | 165,000 | 1,184 | 45 |
| C9 | 6 | 298,000 | 1,364 | 27 |
| C10 | 9 | 505,000 | 1,651 | 19 |
| C11 | 12 | 900,000 | 1,714 | 12 |
| C12 | 15 | 1,600,000 | 1,925 | 8 |

점들을 매끄럽게 펴면 **R(t) = -13 + 2,896·t²** 이다(가중 R² = 0.966).
아래쪽은 평평하고 위로 갈수록 가파르다. 약한 설정끼리는 둘 다 실수를 해서
승패가 뒤집히고, 그래서 점수 차이가 작게 나오기 때문이다.

### 27칸을 어디에 앉혔나

간격을 `t` 가 아니라 **레이팅**으로 고르게 잡았다. `t` 로 고르게 나누면 실제
실력 차이가 아래쪽은 촘촘하고 위쪽은 듬성듬성해진다.

두 구간으로 나눴다.

| 구간 | 범위 | 한 칸 |
|---|---|---|
| 급 (18급~1급) | t=0 부터 한 수 15만 노드까지 | 약 **55점** |
| 단 (1단~9단) | 그 위부터 끝까지 | 약 **225점** |

왜 한 줄로 고르게 펴지 않았나. 엔진끼리의 레이팅은 약한 쪽에서 납작해지는데,
그 납작함을 그대로 믿고 펴면 급수 대부분이 사람이 이길 수 없는 구간에 몰린다
(실제로 해보니 11급이 한 수에 10만 노드를 보게 됐다). 하지만 사람 눈에는
Skill -20(기물을 그냥 내준다)과 Skill -8(포진은 갖춘다)이 전혀 다른 상대다.
그래서 사람이 이길 수 있는 아래쪽에 급 18칸을 몰아주고, 그 위는 단 9칸이 훑게 했다.

**이 방법의 한계도 적어둔다.**

- 곡선이 `a + c·t²` 꼴로 정해지면, 레이팅을 고르게 나눈 지점은 `t = √(k/n)` 이
  되어 **a 와 c 가 무엇이든 같은 자리**가 나온다. 그러니 1,120판이 급수의 위치를
  직접 찍어준 것은 아니다. 1,120판이 정한 것은 세 가지다 — 사다리가 실제로
  단조롭다는 것, 강도가 자라는 **모양**(자유 2차식은 t=0 에서 아래로 꺾여
  쓸 수 없었다), 그리고 **한 칸이 몇 점짜리인가**.
- 위쪽 기준점(C9~C12)은 한 판에 수 분씩 걸려 8~27판밖에 못 뒀다. 단 구간의
  간격은 급 구간만큼 단단하지 않다.
- 2단 위쪽(t > 0.87)은 아예 붙여보지 못했다. 같은 곡선을 연장해서 쓴다.

같은 자료를 다시 계산하려면:

```bash
node scripts/ladder-selfplay.mjs --from ladder-result.json
```

### 이름에 대하여

**공인 급수가 아니다.** 장기 급수 이름을 빌려 왔을 뿐 이 앱 안에서만 쓰는 눈금이고,
화면에도 그렇게 적어뒀다. 실제 18급이 여기 18급을 이길지는 재본 적이 없다.
붙여본 것은 엔진끼리이지 사람과가 아니다. 급수마다 붙은 한 줄 설명도 그 설정의
'느낌' 을 적은 것이지 측정한 값이 아니다.

## 이길 확률은 어떻게 뽑나

평가치를 로지스틱 곡선으로 확률에 옮긴다. `p = 1 / (1 + e^(-K·score))`.

**K 는 어림값이다.** 제대로 맞추려면 "이 점수에서 시작한 판이 실제로 몇 번 이겼는가"
를 수천 판 모아야 하는데 장기에는 그런 공개 자료가 없다. 체스에는 있어서 lichess 같은
곳이 실측으로 맞춰 쓰지만, 장기 평가치를 체스 계수에 그대로 넣으면 엉뚱한 숫자가 나온다.

대신 **척도만 실제로 쟀다.** 시작 국면에서 한의 차 하나를 뺀 판을 엔진에게 물으면

| | |
|---|---|
| 기물 점수 차 | 11.5점 (차 13점 − 덤 1.5) |
| 엔진 평가치 | **+9.60** |

이 나온다. 즉 엔진이 말하는 1.0 은 장기 점수로 약 1.2점이다. 이 자리가 85% 로
나오도록 K 를 잡았다 — 차 하나를 그냥 앞선 판은 거의 이겼지만 아직 둘 것이 남은
판이라는 뜻이다.

그래서 이 숫자는 **눈금이지 예측이 아니다.** 순서를 읽는 데(어느 수가 더 나은지,
격차가 큰지 작은지) 쓰라고 있는 것이지 "62% 니까 열 판 두면 여섯 판 이긴다" 로
읽으라고 있는 것이 아니다. 화면에서도 단정적으로 쓰지 않는다.

## 복기는 무엇을 근거로 설명하나

설명은 전부 **엔진에서 나온 사실만** 엮어서 만든다. 쓰는 재료는 넷이다.

- 엔진이 고른 최선수와 그 이후 수순
- 실제로 둔 수
- 두기 전과 둔 뒤의 평가치 차이 (= 손해)
- 그 수 이후 상대가 무엇을 잡는가

포진 이름이나 전략 해설은 붙이지 않는다. 지어내게 되고, 복기에서 틀린 설명은
아무 설명도 없는 것보다 해롭다.

### 손해를 장기 점수로 읽어도 되는 이유

초기 국면에서 기물을 하나씩 빼고 40만 노드로 평가시켜 눈금을 재봤다.

| 뺀 기물 | 장기 점수 | 엔진 점수 |
|---|---|---|
| 병 | 2점 | +2.30 |
| 마 | 5점 | +4.54 |
| 포 | 7점 | +5.20 |
| 차 | 13점 | +9.42 |

낮은 쪽에서는 엔진 점수 1.0 이 대략 장기 1점이고, 위로 갈수록 눌린다. 그래서
등급 경계를 점수로 그을 수 있다.

| 손해 | 등급 |
|---|---|
| 엔진과 같은 수 | 최선수 ★ |
| 0.3 미만 | 좋은 수 |
| 0.3 ~ 1.0 | 부정확 ?! |
| 1.0 ~ 3.0 | 실수 ? |
| 3.0 이상 | 악수 ?? |

손해를 기물로 옮길 때는 경계가 흐릿해서(마 4.54 vs 포 5.20) 폭을 넓게 잡고
"마나 포 한 짝쯤" 처럼 말한다.

외통 점수는 그대로 빼면 손해가 수백이 되므로 ±20 으로 자른다. 이기는 외통에서
더 빠른 외통으로 바뀐 것뿐인데 악수로 찍히면 곤란하기 때문이다.

## 좌표와 기보

장기 기보 방식을 그대로 쓴다. 세로줄은 왼쪽부터 1~9, 가로줄은 위에서부터 1~9 와
0(열째 줄). 좌표는 **가로줄을 먼저** 읽는다. 그래서 초의 궁 자리는 95, 한의 궁
자리는 25다. 한 수는 `출발좌표 기물 도착좌표` 로 적는다 — 예: `03馬84`.

**판에는 좌표 숫자를 그리지 않는다.** 실물 장기판에 없기도 하고, 숫자 자리를
비우면 그만큼 격자가 커진다(판 넓이의 86% → 89%). 칸 이름이 필요하면 교차점에
마우스를 올리면 뜬다.

대신 **기보에 마우스를 올리면 그 수가 판에 화살표로 뜬다.** 숫자를 지웠더니
"75卒65" 가 어디인지 알 방법이 없어졌는데, 누르면 알 수 있지만 그러면 국면이
그리로 옮겨간다. 보던 자리를 그대로 두고 어디인지만 알려면 이게 필요하다.

엔진은 내부적으로 체스식 좌표(a1~i10)를 쓰고, `src/janggi/notation.ts` 가 둘
사이를 옮긴다.

규칙은 UI 에 구현하지 않았다. 합법수는 전부 엔진에게 `go perft 1` 로 물어본다.
마의 멱, 상의 길, 궁성 사선, 포가 포를 못 넘는 것까지 엔진이 유일한 근거다.

엔진에는 현재 FEN 만이 아니라 **시작 국면과 둔 수를 함께** 넘긴다. 장기의
장군반복 금지와 빅장 규칙은 "어떤 수순으로 여기까지 왔는가"를 봐야 판정되기
때문이다. 실제로 같은 판이라도 수순을 함께 주면 합법수가 달라진다.

`src/janggi/` 는 엔진 구현을 모른다. 복기가 엔진을 써야 해서 `review.ts` 만
예외인데, 거기서도 클래스를 통째로 받지 않고 필요한 두 메서드(`analyzeOnce`,
`probe`)만 인터페이스로 받는다.

## 테스트

```bash
npm test
```

브라우저도 엔진도 없이 도는 순수 로직만 덮는다(Vitest, 160개). 화면과 엔진은
띄워봐야 아는 것이라 여기서 다루지 않는다.

## 기물과 판

실물 장기알은 상아빛 팔각 나무토막이고, 옆면 두께가 보인다. 그래서 기물을 세 겹으로
그린다.

1. **옆면** — 같은 팔각형을 아래로 조금(반지름의 10%) 밀어 어둡게. 이게 두께다.
2. **테** — 위에서 빛을 받는 빗면. 왼쪽 위가 밝고 오른쪽 아래가 어둡다.
3. **윗면** — 글자를 새기는 평평한 면.

여기에 바닥 그림자(`feDropShadow`)를 깔아야 판 위에 '얹힌' 것처럼 보인다.
그림자와 빛깔은 SVG `<defs>` 에 미리 정의해 두어야 해서 `PieceDefs` 로 빼 놓았고,
기물을 그리는 `<svg>` 마다 한 번씩 넣는다. 카드에 늘어놓는 잡은 기물처럼 아주
작게 그릴 때는 빗면도 그림자도 보이지 않으므로 단색으로 그린다(`flat`).

판은 밝은 대나무색에 아주 옅은 세로 결을 깔았고, 격자선은 불투명하게 올렸다.
예전에는 투명도 0.72 라 흐릿했는데, 실물 장기판의 선은 또렷하다.

글자는 지름의 0.58 에서 **0.64** 로 키웠다. 작으면 멀리서 무슨 기물인지 안 보인다.

## 기물 글자

실물 장기판처럼 **초(楚)는 초서체(흘림), 한(漢)은 해서체(정자)** 로 새긴다.
색도 실물대로 초가 초록, 한이 빨강이다. 한국 장기 앱 중에는 초를 파랑으로
쓰는 것도 있지만, 초서체 글자를 실물 기준으로 만들어 뒀으므로 그쪽을 따랐다.
유니코드에는 초서 글자가 따로 없어서 폰트로는 이 구분을 낼 수 없다. 그래서
글자를 SVG 도형으로 들고 있다(`src/janggi/glyphs.ts`). 출처는 `NOTICE.md` 참고.

기보는 양쪽 모두 정자로 적는다 — `03馬84` 처럼.

## 진영 표기

Fairy-Stockfish 의 대문자(White)가 **초(楚)**, 소문자(Black)가 **한(漢)** 이다.
초가 선수이고 한이 1.5점 덤을 받는 장기 규칙과 맞다. 화면에서는 초가 초록,
한이 빨강이며 초가 아래쪽에 앉는다(판 뒤집기로 바꿀 수 있다).
