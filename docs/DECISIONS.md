# 기술 기록

무엇을 골랐는지보다 **무엇을 버렸고 왜 버렸는지**, 그리고 **원인을 어떻게 찾았는지**를
남긴다. 코드를 보면 알 수 있는 것(무엇을 했나)은 적지 않는다. 코드를 봐도 알 수 없는
것(왜 그렇게 했나, 무엇을 시도했다 접었나)만 적는다.

몇 달 뒤의 나와, 이 프로젝트를 처음 보는 사람이 독자다.

## 쓰는 법

세 갈래로 나눠 적는다. 새 항목은 각 절의 **맨 아래**에 붙인다(시간순).

- **결정** — 갈림길에서 한쪽을 골랐을 때. `상황 / 고른 것 / 버린 것 / 대가`
- **사건** — 버그를 쫓았을 때. `증상 / 찾아간 길 / 원인 / 고친 방법 / 배운 것`
- **되돌린 것** — 했다가 물렀을 때. 판단이 바뀐 이유를 적는다.

항목마다 커밋 해시를 단다. 숫자는 실제로 잰 값만 적고, 어림한 값은 어림이라고 밝힌다.

## 규칙을 UI 에 만들지 않고 엔진에 물어본다

`135a33a` · 2026-09-19

장기 규칙에는 판만 봐서는 판정할 수 없는 것이 있다. 장군반복 금지와 빅장은 "어떤
수순으로 여기까지 왔는가" 에 달려 있다. 같은 판이라도 수순이 다르면 합법수가 달라진다.

**고른 것** — 합법수를 전부 엔진에 `go perft 1` 로 물어본다. UI 는 규칙을 모른다.
엔진에 국면을 넘길 때 FEN 만이 아니라 시작 국면 + 수순을 함께 넘긴다.

**버린 것** — UI 에 규칙 엔진을 직접 구현하는 것. 장기 기물 열두 종의 이동 규칙만이면
할 만하지만, 위의 두 규칙까지 맞추려면 사실상 엔진을 다시 짜게 된다.

**대가** — 엔진 응답이 오기 전에는 판정을 미뤄야 한다(`ready` 플래그). 이걸 빼먹으면
"둘 수가 없음" 을 대국 종료로 오해한다. 엔진이 뜨지 않으면 판 자체가 돌지 않는다.

이 선택 덕에 외통 판정 같은 미묘한 자리를 UI 가 몰라도 됐다. 다만 장기에는 한수쉼이
있어서 "둘 수가 하나도 없음" 이 외통이 아니다 — 엔진은 외통에서도 한수쉼 하나는
내놓는다. 그래서 판정 기준을 "장군인데 한수쉼 말고는 둘 게 없음" 으로 잡았다.

## UCI_Elo 를 버리고 Skill Level + 노드 수로 급수를 만든다

`cc1de53` · 2026-09-21

엔진에 `UCI_LimitStrength` / `UCI_Elo`(500~2850) 가 있어서 이것부터 시험했다.

**실측 결과 안 먹혔다.** 장기 변형에서 Elo 500 과 2850 을 각각 돌리면 **둘 다
depth 15~16 으로 똑같이 멀쩡한 수**를 냈다. 이 환산표는 체스용으로 맞춰진 것이라
장기에는 눈금이 붙지 않는다. 숫자만 그럴듯하고 실제로 약해지지 않아서 버렸다.

**Skill Level 은 먹혔다.** 초기 국면에서 여섯 번씩:

| Skill | 서로 다른 수 | 비고 |
|---|---|---|
| 20 | 1/6 | 여섯 번 다 같은 최선수 |
| 0 | 3/6 | |
| −20 | 2/6 | 최선수를 아예 안 고름 |

종반 국면에서는 Skill −20~−5 가 여덟 번 중 여덟 번 궁만 제자리에서 꼬물거렸다.
초보가 두는 모양이 실제로 나온다.

**시간이 아니라 노드로 자른다.** 시간으로 자르면 빠른 PC 의 3급이 느린 PC 에서는
5급이 된다. `go nodes` 는 정확히 그 수에서 끊긴다(요청 1,000 → 실제 1,000,
요청 100만 → 실제 1,000,679). 노드로 자르면 어느 기기에서나 같은 급수다.

## 27칸 급수의 간격을 자가대국으로 쟀다

`770d4c1` · 2026-09-23

11단계를 27단계(18급~1급, 1단~9단)로 늘렸다. **문제는 만드는 게 아니라 검증이었다.**
27칸으로 자르면 이웃한 두 칸의 차이가 아주 작아서, 한 쌍을 직접 확인하는 데만 수백
판이 필요하다. 쌍이 26개면 며칠을 부어도 모자란다.

**순서를 뒤집었다.**

1. 두 손잡이(Skill Level, 노드)를 하나의 강도 곡선 `t` 로 묶는다
2. 그 위에 확실히 구분되는 기준점 13개를 찍고 서로 붙인다
3. 승패를 Bradley-Terry 로 풀어 기준점마다 레이팅을 낸다
4. 그 레이팅 눈금 위에 27칸을 앉힌다

6코어 PC 에서 네 판씩 동시에 **85분, 1,120판**. 상차림 16가지를 돌리고 색을 번갈아
잡았다.

- 이웃 쌍 12개 + 한 칸 건너뛴 쌍 11개 = **23쌍 전부 위쪽이 앞섰다. 역전 0**
- 이웃 쌍 593판에서 위쪽 승률 **61.0%**
- 한 칸 건너뛴 쌍 527판에서 **72.6%**
- 레이팅 곡선 `R(t) = -13 + 2,896·t²` (가중 R² = 0.966)

아래쪽 쌍 하나만 떼어보면 100판에 53% 라 **그것만으로는 유의하지 않다.** 하지만
23쌍이 모두 같은 방향일 확률은 1,200만 분의 1이고, 두 칸 차이는 65~66% 로 분명히
갈린다. 한 칸은 작고 두 칸은 확실한 눈금이다.

**레이팅만 믿지는 않았다.** 엔진끼리의 레이팅은 약한 쪽에서 납작해진다(둘 다 실수하니
승패가 뒤집힌다). 그대로 펴면 11급이 한 수에 10만 노드를 보게 된다. 사람 눈에는
Skill −20 과 −8 이 전혀 다른 상대다. 그래서 사람이 이길 수 있는 아래쪽(15만 노드까지)에
급 18칸을 몰아주고 그 위를 단 9칸이 훑게 했다. 급 한 칸 55점, 단 한 칸 225점이다.

## 이길 확률의 계수를 추측에서 실측으로 바꿨다

`b602512` · 2026-09-27

평가 점수를 `p = 1/(1+e^(-K·score))` 로 확률에 옮기는데, 처음에 `K` 를 눈대중으로
잡았다. 그러면 화면에 나가는 "62%" 가 아무 근거 없는 숫자가 된다.

**앵커를 만들어 쟀다.** 시작 국면에서 한의 車 하나를 뺀 판(장기 점수로 11.5점 차)을
만들어 엔진 평가를 읽으니 **+9.60** 이었다. 그 국면이 85% 쯤 되도록 K 를 맞췄다.
덤으로 엔진 1.0 ≈ 장기 1.2점이라는 환산도 얻었다.

주석·README·테스트에 "이 값은 이렇게 쟀다" 를 함께 적었다. 안 적으면 다음 사람이
또 눈대중으로 고친다.

사실은 남기고 되살릴 때 그 쪽만 소진 상태로 만든다.

## 끝나는 길 다섯 가지를 한 함수가 답한다

`a1c8a49` · 2026-09-28

대국이 끝나는 길이 다섯이다 — 외통·수몰·200수 점수·기권·시간패. 이 목록을 쓰는 곳마다
따로 들고 있었고, **세 군데가 각자 다른 것을 빠뜨렸다.**

| 자리 | 빠진 것 | 증상 |
|---|---|---|
| 기보 저장 | 시간패·점수 | 승부가 `unfinished` 로 저장 |
| 대국 패널 결과 줄 | 수몰·점수 | 판이 끝났는데 아무 말도 없음 |
| 기권 버튼 비활성 | 수몰·점수 | 끝난 판에서도 눌림 |

같은 실수가 세 번 따로 났으면 사람이 부주의한 게 아니라 **목록을 나눠 가진 것이 원인**이다.
`outcomeOf` 한곳에서 답하고 셋 다 거기에 묻게 했다.

## 분석에서는 끝난 판도 둘 수 있다

**고른 것** — 연 판의 '파일로 저장' 옆에 '링크 공유'. 받는 쪽 동작, 건네는 방식, 파일 이름은
사용자가 골랐다 - 받으면 목록에 넣고 바로 연다, 폰은 공유 창·컴퓨터는 복사, `janggi/share.ts`.

- **주소의 `#` 뒤에 담는다.** `#` 뒤는 서버로 가지 않고 받은 쪽 브라우저만 읽는다. 서버가 없는
  지금 그대로 되고, 판이 서버 기록에 남지도 않는다.
- **싣는 것은 시작 국면·수순·규칙·두 사람·승부뿐.** 기보 표기는 수순에서 다시 만들 수 있고
  (`gameOfRecord` 가 이제 늘 다시 만든다), 평가치·복기는 받은 쪽이 복기를 돌려 얻는다. 이것을
  JSON 으로 적어 deflate(`CompressionStream`)로 줄이고 base64url 로 적는다. 24수 판이 346자,
  수를 뒤섞은 200수 판이 903자.
- **앞에 형식 번호(`1.`)** - 담는 모양을 바꾸면 올린다. 이미 건넨 링크는 옛 번호로 남아 있다.
- **받는 쪽은 파일과 같은 길을 지난다** - `readRecord`(형식) → `gameOfRecord`(국면) → 엔진의 규칙
  검사. 받은 링크는 누가 고쳤을지 모르는 값이다.
- **같은 판을 또 받으면 새로 넣지 않고 그 판을 연다**(시작 국면과 수순이 같으면 같은 판). 읽은
  링크는 주소에서 지운다 - 새로고침마다 또 넣지 않게. 앱이 떠 있는 탭에 링크를 붙여 넣으면 페이지가
  새로 읽히지 않고 `#` 뒤만 바뀌므로 `hashchange` 도 듣는다.

확인: 컴퓨터에서 복사한 링크를 빈 브라우저에서 열어 기보 표기 24수와 국면 25개가 같은 것, 같은
링크를 두 번 열어도 목록이 1판인 것, 잘린 링크의 까닭이 목록 제목 줄에 서는 것, 폰(390·360)에서
공유 창이 제목·주소를 받는 것.

**버린 것** — 주소의 `?` 뒤(쿼리)에 담기: 서버로 가서 기록에 남는다. 표기·평가치까지 싣기: 주소가

**대가** — 링크는 앱이 떠 있는 주소를 그대로 쓴다. 지금처럼 내 컴퓨터(`localhost`)에서 띄웠으면

## 기보 표기 옆에 풀어 쓴 한 줄을 붙이고, 등급 기호를 뺀다

2026-09-30

**상황** — "59차69 이게 무슨 뜻이야? ?? 악수도 무슨 뜻이야?" 라는 물음을 받았다. 만든
쪽에서는 당연했지만 **쓰는 쪽에서는 둘 다 읽을 수 없는 기호**였다.

**표기** — `59차69` 는 앞 두 자리가 출발, 뒤가 도착이고 각 자리는 `가로줄 세로줄` 순서다.
장기 기보의 표준 표기라 바꾸지는 않되, 아래에 풀어 쓴 한 줄을 붙였다("졸을 앞으로 1칸
옮겼습니다."). 표기를 못 읽어도 무슨 수였는지는 알 수 있다.

**'위/아래' 가 아니라 '앞/뒤'** — 판은 뒤집을 수 있어서 위아래가 보는 사람마다 다르다.
앞뒤는 둔 쪽이 정해지면 하나로 정해진다. 초는 가로줄 번호가 작아지는 쪽이, 한은 커지는
쪽이 앞이다.

**등급 기호** — `★ · ?! ? ??` 를 뺐다. 체스에서 온 표기라 배경 지식을 요구하는데, 무엇보다
**바로 옆에 "악수" 라고 이름이 적혀 있어서 같은 말을 한 번 더 하는 것**이었다. 등급은
이름과 색으로만 말한다.

**한 번 틀렸다** — 조사 헬퍼 `을를(w)` 이 조사만 돌려주는 줄 알고 `${piece}${을를(piece)}`
로 적었더니 화면에 "**사사를** 앞으로 1칸" 이 떴다. `을를` 은 낱말까지 함께 돌려준다
("사" → "사를"). 브라우저에서 실제 글자를 읽어 보지 않았으면 그대로 나갔다.

## 형세 그래프를 빼고, 수 이동을 슬라이더로 옮긴다

2026-09-30

**상황** — 판 전체의 승률 흐름을 잇는 선 그래프가 있었다. "수가 많아지면 매우 안 좋게
보인다" 는 말을 들었다.

**왜 그런가** — 그래프는 100 폭에 수를 모두 늘어놓는다. 40수면 한 수가 2.5px 이고 100수면
1px 이다. 점이 빽빽하게 들어차 선이 지저분해지고, **'어디서 기울었나' 를 한눈에 보라는
원래 목적이 되레 흐려진다.** 수가 적을 때만 쓸모 있는 그림이었다.

**고른 것** — 그래프를 빼고, 형세는 지금 국면의 승률(퍼센트 + 두 색 막대)만 남긴다.

**옮긴 것** — 그래프는 '그 수로 건너뛰기' 도 겸하고 있었다. 그냥 빼면 이전·다음만 남아
60수짜리 판에서 30수를 보려면 30번 눌러야 한다. 그래서 **판 조작 줄에 수 슬라이더**를
뒀다. 수가 몇이든 모양이 변하지 않는다.

**오히려 나아진 것** — 그래프는 복기를 돌린 뒤에야 떴다(평가치가 없으면 그릴 것이 없다).
그래서 **복기 전에는 건너뛸 방법이 아예 없었다.** 슬라이더는 복기와 무관하다. 자리를 옮기고
보니 애초에 이쪽이 맞았다.

**두는 중인 대국에는 두지 않는다** — 거기서 뒤로 가는 것은 '무르기' 라 내 차례까지 되감는
규칙이 따로 있다. 끌어서 아무 데나 가면 그 규칙과 어긋난다.

보험이다. 그렇게 사용자에게도 같이 말했다.

**배운 것** — 근거 없이 버린 방법은 기록에 '버림' 으로 남아 다시 검토되지 않는다. 버릴
때는 무엇을 확인하지 않았는지도 같이 적어야, 다음에 그것부터 확인하게 된다.

## 오른쪽 칸 높이를 기보 탭에서도 판에 맞춘다

2026-09-30

**상황** — 대국 탭은 오른쪽 칸 아래 끝이 판 아래 끝과 맞는데(**대국 탭의 오른쪽 칸은 판
높이** 절), 기보 탭은 내용만큼만 서서 아래가 떴다. 사용자가 짚었다.

**고른 것** — `.side-col` 전체를 판 높이(`--board-h`)로 두고, 남는 높이를 탭마다 다른 것이
먹게 했다. 대국은 대국자 카드 두 장(시계가 커진다), 기보는 맨 아래 복기 패널이다.

**왜 복기 패널인가** — 그 칸에서 제일 긴 글이 복기 설명이라 **늘어날 자리가 필요한 것도
거기**다. 기보 탭의 대국자 카드는 시계가 멎어 있어 키워도 빈 카드가 커질 뿐이다. 줄어들지는
않게(`flex: 1 0 auto`) 둬서, 내용이 판보다 길어지면 패널이 찌그러지는 대신 칸이 스크롤된다.

**대가, 그리고 바로 다음 날 좁힌 것** — 처음에는 늘 맞췄더니 복기를 돌리기 전에 패널 아래가
비었다(1440에서 230, 1920에서 460). 높이를 맞추면 남는 높이는 **어딘가에 놓일 수밖에** 없다.
사용자가 보고 말했다 — "처음에는 높이를 안 맞추는 게 낫고 펼쳤을 때 맞춰졌으면 좋겠어."
그래서 **복기를 돌린 뒤에만** 맞춘다(`.review.grown`, 2026-10-01). 돌리기 전에는 패널이 제
크기로 서고 칸 아래가 뜬다 - **뜬 바탕이 빈 상자보다 조용하다.** 같은 '빈 자리' 라도 테두리와
그림자가 둘러싸고 있으면 "여기 뭔가 있어야 하는데 없다" 로 읽힌다.

빈 자리를 글로 메우지는 않았다 - 자리를 메우려고 쓴 글은 읽는 사람이 알아보고, 그때부터 그 칸
전체를 읽지 않게 된다. 대신 **원래 필요했던 한 줄**을 넣었다(아래).

## 화면의 말을 두 곳 고쳤다 — 형세 한 줄, 깊이 한 줄

2026-09-30

**상황** — 사용자가 둘을 짚었다. 형세 아래 설명이 길다("왼쪽이 초 몫입니다. 엔진 점수를
옮긴 어림값입니다."). 그리고 복기의 **'깊이' 가 무슨 말인지 모르겠다**.

**고친 것**

- 형세: 한 줄로 줄였다 — "AI가 어림잡은, 지금 이길 가능성입니다." 왼쪽이 초라는 것은 바로
  위에 진영 색으로 "초 69%" 라고 이미 적혀 있다. **화면이 이미 말한 것을 글로 또 말하고
  있었다.**
- 깊이: 고르는 줄 아래에 한 줄을 더했다 — "복기는 한 수마다 엔진을 한 번씩 돌립니다.
  정밀할수록 등급이 믿을 만해지고 그만큼 오래 걸립니다." 아직 한 번도 돌리지 않았을
  때만 적는다(한 번 돌린 뒤에는 위에 설명이 가득 차 있다).

**왜 이건 자리 메우기가 아닌가** — 깊이는 엔진 쪽 말이라 화면만 봐서는 무엇을 고르는
건지 알 수 없고, 모르면 기본값을 그냥 둔다. **사용자가 실제로 물어본 것**을 화면에 적은
것이다. 마침 그 자리가 위의 빈 자리이기도 했다.

**배운 것** — "설명이 길다" 와 "설명이 없다" 가 한 화면에 같이 있었다. 글이 많고 적음이
아니라, 화면이 아직 말하지 않은 것을 글이 말하고 있는지가 기준이다.

## 업데이트 내역을 따로 선 쪽에서 가운데 창으로

2026-09-30

**상황** — 업데이트 내역을 `/updates/` 라는 두 번째 쪽으로 세웠다(**결정** 절). 사용자가
물었다 — "그냥 팝업창으로 띄우면 안되나?"

**고른 것** — 앱 안의 가운데 창(`UpdatesDialog.tsx`)으로 옮기고, 그 쪽과 전용 스타일
(`updates/index.html`, `src/updates/main.ts`, `src/styles/updates.css`), 그리고 빌드의 두 번째
진입점을 지웠다. 목록 데이터(`src/updates/log.ts`)는 그대로 한 곳에 남는다.

**까닭** — 몇 줄 읽고 닫을 글 때문에 **새 탭이 열리고 두던 화면을 떠나야 했다.** 결과
창·확인 창이 이미 가운데 창이라 틀도 이미 있었다. 목록을 그리는 코드가 두 벌이 되는 것도
피했다.

**무엇을 잃었나** — 밖에서 걸 수 있는 주소(`/updates/`)가 없어졌다. 아직 배포 전이라 걸린
링크가 없고, 필요해지면 그때 같은 데이터로 다시 세우면 된다. 엔진을 받지 않고 여는 가벼움도
잃었다 - 그건 두 번째 쪽을 세운 원래 이유였는데, **앱을 이미 열어 둔 사람이 누르는 버튼**이라
실제로는 쓰이지 않는 이점이었다.

**제보 자리는 옮기지 않았다** — 그 쪽 아래에 제보 안내가 있었는데, 제보 버튼이 어느 화면에서나
떠 있어서 창에 또 두면 같은 곳으로 가는 문이 둘이 된다.

## 복기를 두 번에 나눠 본다 — 먼저 재고, 두 길을 버리고

2026-10-01

**상황** — 사용자: "깊이의 추론 속도가 생각보다 너무 오래 걸리는 거 같은데 획기적으로 단축
시킬 수는 없나?"

**먼저 쟀다.** 고치기 전에 엔진이 실제로 얼마나 빠른지부터 봤다(노드에서 wasm 을 직접
띄워서, 그리고 브라우저에서 진짜 복기를 돌려서).

| 스레드 | 50만 노드에 걸린 시간 | 초당 국면 | 그때 닿은 깊이 |
| --- | --- | --- | --- |
| 1 | 2.0초 | 25만 | 18 |
| 2 | 1.0초 | 49만 | 15 |
| 4 | 0.54초 | 92만 | 14 |
| 8 | 0.43초 | 118만 | 12 |

**첫 번째로 드러난 것은 화면이 거짓말을 하고 있었다는 것이다.** `reviewSeconds` 가 초당
25만으로 나누고 있었는데, 그건 **스레드 하나일 때** 값이고 앱은 넷을 쓴다. 40수 기보 정밀
복기에 "약 5분 20초" 라고 적고 실제로는 1분 29초에 끝났다. **3.6배를 부풀려 적고 있었다** -
겁을 줘서 안 누르게 만드는 숫자다. 재서 고쳤다(스레드 하나당 초당 20만, 스레드 수를 곱한다).

**버린 길 둘.** 둘 다 그럴듯했고 둘 다 재 보니 틀렸다.

- **스레드를 더 주기** — 4→8 로 늘리면 초당 국면은 15% 오르는데 **같은 노드로 닿는 깊이가
  14에서 12로 얕아진다.** 스레드가 많을수록 겹쳐 뒤지는 일이 늘어서, 빨라진 만큼 질이
  떨어진다. 바꾼 게 아니라 맞바꾼 것이다.
- **노드 예산 대신 깊이 예산** (`go nodes N` → `go depth D`) — 쉬운 국면에서 일찍 끝나니
  빠를 줄 알았다. 40수 기보로 재니 평균 깊이 16을 노드 예산은 21.1초에, 깊이 예산은
  31.8초에 얻었다. **노드 예산이 이미 더 좋은 분배였다** - 쉬운 국면은 알아서 더 깊이 가고
  어려운 국면은 적당히 끊는다.

**고른 것 — 두 번 훑기.** 1차로 기보 전체를 가볍게(10만) 보고, 승률이 크게 움직인 수만
골라 2차에서 고른 깊이로 다시 본다. 조용히 흘러간 수에 200만 노드를 쓰는 것은 거의 전부
버리는 일이다. 40수 기보 정밀이 1분 29초 → 45초, 100수 기보는 4분 12초 → 1분 28초다.
긴 기보일수록 더 벌어진다 - 1차는 수에 비례해 늘지만 2차는 열다섯 수에서 멈춘다.

**한 수의 두 끝은 늘 같은 깊이로 본 값이어야 한다.** 이게 이 설계의 핵심이다. 등급은 두
국면의 승률 차이로 매기는데, 한쪽만 깊게 보면 **깊이가 달라서 생긴 값 차이가 그대로
'손해' 로 읽힌다** - 없던 실수가 생긴다. 그래서 고른 수는 앞뒤 국면을 둘 다 다시 보고,
고르지 않은 수는 양쪽 다 1차 값으로 둔다.

**자리를 채우려고 끌어오지 않는다** — 다시 볼 수는 승률 하락 2%p 를 넘긴 것 중에서만
고른다. 깨끗하게 둔 판이면 2차가 아예 돌지 않는다(엔진끼리 둔 40수 기보로 재 보니 승률이
1.3%p 도 안 움직여서 정밀 복기가 5.7초에 끝났다). 바닥을 부정확(5%p)보다 낮게 잡은 까닭은,
1차는 얕게 본 값이라 경계에 걸친 수가 2차에서 등급을 넘나들 수 있고 **그 수야말로 다시 봐야
할 수**이기 때문이다.

**대가** — 조용히 흘러간 수는 얕게 본 값으로 남는다. 티 나지 않는 실수를 놓칠 수 있다.
그래서 몇 수를 다시 봤는지 화면에 적는다. 다시 볼 것이 없었을 때도 적는다 - 아무 말이
없으면 고른 깊이로 전부 본 줄로 읽는다.

**덤으로 생긴 것** — 1차가 끝나면 모든 수에 설명이 붙으므로, 2차를 기다리지 않고 바로
읽을 수 있다(17수 기보에서 1차 2.3초, 전체 21.5초). 읽는 동안 중요한 수의 설명이 더
정확한 것으로 바뀐다. 속도를 고치려다 **기다리는 느낌 자체를 없앴다.**

**배운 것** — "느리다" 는 말에 바로 코드를 고치면 틀린 데를 고친다. 여기서 제일 큰 문제는
엔진이 아니라 **화면에 적힌 숫자**였고, 그 다음으로 좋은 길은 더 빨리 뒤지는 것이 아니라
**덜 뒤지는 것**이었다. 그럴듯한 길 둘은 재 보니 아무것도 주지 않았다.

## 제보는 클립보드가 아니라 미리 채운 폼으로

2026-10-01

**했던 것** — 제보 버튼이 버전·창 크기·브라우저·보던 판을 **클립보드에 담고** 빈 폼을 열었다.
보내는 사람이 '환경' 칸에 붙여넣는 몫이었다.

**바꾼 까닭** — 사용자가 폼을 만들고 칸 이름표(`entry.1007014165`)를 줬다. 구글 폼은 주소 뒤에
`?usp=pp_url&entry.NNN=값` 을 붙이면 **그 칸이 채워진 채로 열린다.** 붙여넣기를 시키면 절반은
그냥 비워 둔 채 보낸다 - 보내는 사람에게 할 일을 하나라도 덜 주는 쪽이 받는 쪽에 이롭다.

**열어 보고 하나 고쳤다** — 실제로 그 주소를 열어 칸 값을 읽어 보니 **줄바꿈이 지워져
있었다.** '환경' 이 단답형(`input`)이라 여러 줄이 들어가지 않는다. "장기 AI v0.1.0대국" 처럼
붙어서, 미리 채울 때는 가운뎃점으로 잇는다(클립보드로 갈 때는 그대로 줄바꿈이다).

**이름표가 없으면** 예전처럼 빈 폼을 열고 클립보드에 담는다. 폼을 아직 안 만든 사람(나중의
나, 이 저장소를 받아 가는 사람)에게도 버튼이 쓸모 있어야 한다.

**배운 것** — '열린다' 까지만 확인하면 반만 본 것이다. 받는 쪽 화면에서 **값이 어떤 모양으로
들어가는지**까지 봐야 한다. 열리기는 멀쩡히 열렸고, 글자만 뭉쳐 있었다.

## 폰에서 판이 잘렸다 — `1fr` 의 최소폭

`76af7bd` · 2026-09-27

**증상** — 360px 폭에서 장기판 오른쪽이 화면 밖으로 잘려 나갔다.

**찾아간 길** — 처음에 `.table { width: var(--board-w) }` 를 범인으로 지목했다. **틀렸다.**
`.table` 은 이미 `100%` 였다. 추측을 멈추고 브라우저에서 DOM 을 위로 훑으며 요소마다
실제 폭을 쟀다. 그러자 넘치는 지점이 그리드 트랙이라는 게 나왔고, 후보 CSS 를 하나씩
주입해 확인했다.

**원인** — CSS 그리드의 `1fr` 은 `minmax(auto, 1fr)` 이다. 그 `auto` 최소값이 내용물의
min-content 라서, 종횡비가 고정된 SVG 가 트랙을 뷰포트보다 넓게 밀어낸다.

**고친 방법** — `minmax(0, 1fr)`. `min-width: 0` 을 자식에 주는 것은 **듣지 않았다**
(트랙 자체의 최소값이라서). 같은 버그가 두 파일에 있었다.

**배운 것** — 가설을 세웠으면 고치기 전에 재서 확인한다. 이 건은 첫 가설이 그럴듯했고
틀렸다. 재지 않았으면 엉뚱한 곳을 고쳐놓고 고쳤다고 했을 것이다.

## 무르고 같은 수를 다시 두면 판이 영구히 멈췄다

`0ee0f3a` · 2026-09-27

**증상** — 한 수 두고 → 엔진 응수 → 무르기 → **똑같은 수**를 두면, 엔진이 영영 두지
않는다. 32초를 기다려도 착수도, "생각 중" 표시도, 배너도 없었다. 새로고침 말고는
빠져나올 길이 없다.

**원인** — 엔진이 같은 국면에서 두 번 두는 것을 막으려고 "이 국면에서 이미 뒀다" 를
적어두는데, **무를 때 그 기억을 버리지 않았다.** 무르면 그 국면이 되돌아오므로 기억이
그대로 들어맞아 계속 건너뛴다.

**고친 방법** — 무르기에서만 기억을 지우면 기보 이동·기보 불러오기에 같은 구멍이 남는다.
그래서 기억을 국면에 묶고, **국면을 벗어나는 순간 버리게** 했다. 한 줄로 네 경로가 덮인다.

**배운 것** — 무르기는 바로 앞 세션에서 "무르면 엔진 차례에 멈춘다" 는 불편을 고치며
손댄 자리다. 고치면서 이 경로를 열었다. 초보가 제일 흔히 하는 행동(무르고 같은 수를
다시 두기)이 하필 그 경로였다.

## 직접 입력 시계를 고르면 엔진이 한 수도 두지 않았다

`0ee0f3a` · 2026-09-27

**증상** — 시계를 '직접 입력' 으로 고르면 엔진이 착수하지 않는다. 엔진 시간만 깎인다.
프리셋 시계에서는 멀쩡하다.

**원인** — `resolveClock` 이 직접 입력일 때 매번 **새 객체**를 만든다(프리셋은 배열 원소를
그대로 돌려줘 참조가 안정적이다). 그 값이 '엔진이 쓸 시간' 을 정하는 effect 의 의존성에
들어 있어서, 메모하지 않으니 렌더마다 effect 가 돌았다. 시계가 200ms 마다 깎이므로
예산이 계속 바뀌고 → 탐색 설정 키가 바뀌고 → 탐색이 멈췄다 180ms 뒤 다시 시작한다.
**탐색이 끝날 틈이 없었다.**

**확정한 방법** — 대조 실험. 같은 국면·같은 급수에서 직접 입력으로 15초 무착수를 확인한
뒤, 시계만 프리셋으로 바꾸자 **즉시** 착수했다. 변수를 하나만 바꿔서 원인을 좁혔다.

**아이러니** — 그 자리의 코드 주석이 "시계 값을 탐색 한계에 그대로 물리면 탐색이 처음부터
다시 시작되므로 한 번만 정하고 붙잡아 둔다" 라고 **막겠다고 적어둔 바로 그 현상**이었다.
의도는 맞았는데 객체 정체성 때문에 새어 나갔다.

**놓친 이유** — 이 기능을 넣은 커밋에서 프리셋으로만 확인했다. 새로 넣은 경로를 새로
확인하지 않았다.

## 시간패가 새로고침으로 사라졌다

`0ee0f3a` · 2026-09-27

**증상** — 시간패로 진 판을 새로고침하면 패배가 사라지고 그대로 이어서 둘 수 있다.
**진 판을 새로고침으로 무를 수 있었다.**

**원인** — 두 겹이었다. 저장은 하면서 복원은 기권만 했고, 설사 복원해도 마운트 때 도는

## 판이 커지자 판 위아래에 빈 테두리가 생겼다

1024×768 도 같았다(상자 712, 그림 576).

**원인** — 판은 `height: 100%; width: auto; max-width: 100%` 로 서 있었다. 폭이 모자라면
`max-width` 가 폭만 줄이고 높이는 100% 그대로라 상자가 그림보다 길어진다. 예전에도 같은

**고친 방법** — 넓은 화면에서 판 자리를 크기 컨테이너(`container-type: size`)로 두고
판 폭을 `min(100cqw, 100cqh × 556/618)`, 비율을 `aspect-ratio: 556/618` 로 박았다. 폭과
높이 가운데 모자란 쪽에 맞춰 판 비율 그대로 그린다. 폭에 걸린 판은 위에 붙여 오른쪽 칸

## 엔진이 장군을 피한 수에 "멍군!" 을 외쳤다 — 한 번 늦게 꺼지는 probed

돈다. 그래서 수를 둔 직후 한 번은 국면 번호는 새것인데 `probed` 는 여전히 true, `checkers` 는

**원인** — 응답이 어느 국면의 것인지 꼬리표 없이 '받았다' 는 불(bool)만 들고 있었다. 분석
결과(`snapshot`)에는 이미 국면 꼬리표가 붙어 있었는데 합법수·장군 쪽에는 없었다.

**고친 방법** — 합법수·장군을 받은 국면의 key 와 함께 저장하고, 지금 국면의 key 와 같을
때만 `probed = true` 로 내보낸다. 다르면 빈 합법수·빈 장군을 준다. 단순 장군 → "장군!" 만,
막으면서 되받은 수(포로 막으며 졸 너머로 부른 수) → "멍군!", 엔진이 피한 수 → 아무 말 없음을

**놓칠 뻔한 것** — 멍군 검사용 첫 국면이 통째로 움직이지 않았다(궁을 골라도 갈 곳이 없음).

틀린 것이었다. 궁 사이를 비우지 않는 국면(포가 졸 너머로 부르는 멍군)으로 바꿨다.

**배운 것** — 비동기 결과는 '받았는가' 가 아니라 '**무엇에 대해** 받았는가' 를 들고 다닌다.
불 하나로 들면 값이 바뀌는 순간과 불이 꺼지는 순간 사이에 틈이 생긴다.

내 패가 됐다. 표준에서는 점수로 초가 이겨야 할 판이 초의 패로 뒤집힐 수 있었다.

**원인** — 판정이 '장군 아닌데 둘 수 0 = 수몰' 하나뿐이었다. 장기에는 한수쉼이 있어서 장군만 아니면

점수로(엔진의 판정과 같다 - 차이가 1.5 를 넘으면 초), 전통이면 비김. 수몰은 둘 다 아닐 때만 남긴다.
테스트의 국면과 합법수는 엔진에 물어 받은 값 그대로 옮겼다. 고친 뒤 같은 판을 실제 엔진과 다시
둬서 "비겼습니다 · 빅장 - 비겼습니다" 와 기보 목록의 무승부를 확인했다.

**놓칠 뻔한 것** — 기보 목록은 읽어 올 때 결과 종류를 배열로 걸렀다. 거기에 빅장·양쪽 한수쉼을
빠뜨려서, 그렇게 끝난 판이 **새로고침하면 목록에서 사라질** 참이었다. 타입 검사는 배열의 빠진
원소를 잡지 못한다. 종류마다 키를 두는 표(`Record<ArchivedKind, true>`)로 바꿔 다음에 끝나는 길을
늘릴 때는 컴파일에서 걸리게 했다.

**배운 것** — '0 이면 X' 같은 판정은 0 이 되는 길을 엔진에 전부 물어 본 뒤에 쓴다. 이 앱은 규칙을
엔진에 맡겼으면서 결과 해석은 앱이 추측하고 있었다.

## 로그인 — 붙이지 않기로 (지금은)

2026-09-29

로그인은 이 프로젝트의 목적(서버를 운영해 본다)에 정확히 맞는 기능이다. 그런데 지금
붙이지 않기로 했다. 세 가지 때문이다.

**서버가 아예 없다.** 지금 앱은 100% 브라우저에서 돈다. 로그인을 붙이는 순간 백엔드 ·
DB · 세션 · 배포 · 운영이 한꺼번에 따라온다. 장기 앱을 만드는 일이 아니라 백엔드를
만드는 일이 된다.

**COOP/COEP 와 충돌한다.** 이게 이 프로젝트만의 함정이다. SharedArrayBuffer 때문에
`Cross-Origin-Opener-Policy: same-origin` 을 걸어뒀는데, 이 헤더가 **팝업 방식 소셜
로그인을 깨뜨린다.** COOP same-origin 이면 팝업창의 `window.opener` 가 끊겨서 구글 ·
카카오 로그인 팝업이 결과를 돌려주지 못한다. 리다이렉트 방식으로 우회하고 콜백 경로의
헤더를 따로 빼야 한다. 엔진이 안 돌거나 로그인이 안 되거나 둘 중 하나가 되기 쉽다.

**로그인 = 개인정보 수집이다.** 비상업이어도 이메일 하나만 받아도 개인정보처리방침이
필요하다.

**대신 정한 순서** — 로그인이 없으면 **불가능한 가치**가 생겼을 때 붙인다. 기보 저장은
localStorage 로 이미 된다. 그 다음 단계로 생각하는 것은 **기보를 URL 에 담는 공유 링크**다
(`b71cfb0` 에서 넣었다 - 위 *결정* 참고).
서버 없이 되고, "이 판 좀 봐줘" 로 사람이 들어온다. 로그인이 주는 가치의 절반을 서버 없이
가져온다. 그 뒤에도 "기기를 옮겨도 내 전적이 남는다" 를 원하는 사람이 실제로 생기면,
그때 소셜 로그인 하나만 붙인다. 비밀번호는 직접 받지 않는다.

## `.gib` 기보 읽기 — 보류

다른 장기 앱에서 둔 판을 여기서 복기하게 하면 유입 고리가 된다. 다만 **카카오장기가 기보를
내보내주는지 확인되지 않았다.** 내보내기가 없으면 고리 자체가 성립하지 않는다. 포맷 명세를
짐작해서 파서를 쓰면 실제 파일에서 깨지므로, 확인 전까지 시작하지 않는다.

## 버려도 된다고 판단한 것

- **박보·묘수풀이** — 검증된 문제 없이 만들면 답이 틀린 문제를 내게 된다. 경쟁 앱에 다 있고,
  이 앱의 정체성(분석·복기)과도 무관하다.
- **포진법 통계** — 포진 통계는 사람 모집단을 상대로 둘 때 의미가 생긴다. 엔진과 혼자 둔
  판으로는 해석할 수 없는 숫자만 나온다.

# 반복해서 통한 방법

앞으로도 쓸 것들. 전부 이 프로젝트에서 실제로 효과를 본 순서다.

**추측을 세웠으면 고치기 전에 잰다.** `1fr` 건은 첫 가설이 그럴듯했고 틀렸다. 브라우저에서
DOM 을 훑고 후보 CSS 를 주입해 보고서야 진짜 원인이 나왔다.

**변수를 하나만 바꾸는 대조 실험.** 직접 입력 시계 건은 "시계 종류만" 바꿔서 원인을 한 번에
좁혔다. 추론으로는 확신할 수 없던 것이 실험 하나로 확정됐다.

**숫자는 앵커를 만들어 잰다.** 승률 계수도, 급수 눈금도 눈대중으로 정할 수 있었다. 아는 값을
가진 국면을 일부러 만들어 재니 근거가 생겼고, 그 근거를 주석에 남기니 다음에 또 눈대중으로
고치지 않게 됐다.

**같은 실수가 세 번 나면 사람이 아니라 구조를 고친다.** 끝나는 길 다섯 가지를 세 군데가 각자
빠뜨렸다. 하나씩 고치는 대신 목록을 한곳으로 모았다.

**고친 자리 근처를 다시 본다.** 엔진 고착은 바로 앞 세션에서 무르기를 고치며 열린 구멍이었다.
새 기능을 넣은 경로는 새로 확인해야 한다 — 직접 입력 시계를 프리셋으로만 확인한 것이 그 반례다.

**보고 전에 한 번 더 잰다.** "기권 후에도 둘 수 있다" 는 없는 버그였다.
